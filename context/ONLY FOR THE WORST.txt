## What Was Built

### 1. The Scoring Engine (`computeRelevanceScore`)

The heart of everything. Every single result — bill, blog, resource, discussion — gets scored before it reaches the UI. Three weighted axes:

**Match Score (50%)**
Two-layer matching. First, direct query token hits against title and excerpt — if you search "finance bill", every word is tokenised and checked against the haystack. That produces a raw hit ratio (hits / total tokens). Second layer is interest matching — your `areas_of_interest` and `interests` arrays from the profiles table are pulled and cross-referenced against the item's tags. It doesn't just do exact matches — it does substring matching too, so "Taxation" matches a tag of "TaxExemption". The two sub-scores are blended 60/40 (query hit weight vs interest weight) when a query is present. When there's no query (rest state), interest matching takes the full 100%.

**Recency Score (30%)**
A decay curve, not a binary. Content from the last 24 hours scores 1.0. 24–72 hours: 0.85. Up to a week: 0.65. Up to a month: 0.40. Up to 3 months: 0.20. Beyond that: 0.05 — it still surfaces, but gets buried unless the match score is exceptional. This means genuinely relevant old content (a landmark bill from 6 months ago) can still rank above fresh irrelevant content if the match score is strong enough.

**County Score (20%)**
Binary but nuanced. If item county matches user county: 1.0. If they don't match: 0.0. If either is null (item has no county, or user hasn't set one): 0.5 — neutral, neither penalised nor boosted. This means a Nairobi user gets Nairobi-tagged content boosted, but national content (no county tag) doesn't get buried.

**Composite:**
```
relevance = match×0.50 + recency×0.30 + county×0.20
```
Scores are normalised 0–1 and displayed as percentages on each card. This gives you full transparency — you can see exactly why something ranked where it did.

---

### 2. Multi-Table Parallel Search (`executeSearch`)

Four Supabase queries fired simultaneously via `Promise.allSettled`. Not `Promise.all` — deliberately. `allSettled` means if one table query fails (say community_posts has a schema issue), the other three still return. The search never completely breaks.

Each table has its own normalisation function mapping raw Supabase rows into a unified `SearchResult` interface with consistent fields: `id, type, title, excerpt, tags, county, created_at, url, metadata`. The `metadata` field carries type-specific extras — bill number and status for bills, author for blogs, upvotes for discussions.

Query construction uses Supabase's `.or()` with `ilike` — each token becomes a wildcard search across both title and excerpt simultaneously. So a 3-word query generates 6 ilike conditions per table.

---

### 3. Enrichment Chips (`extractEnrichmentChips`)

A civic keyword map hardcoded with 10 domains: finance, bill, election, health, education, land, tax, devolution, rights, water. When your query contains a trigger word, 5 contextually relevant hashtag chips surface beneath the search bar. Tapping one marks it active, it gets appended to the next search execution, and the results narrow accordingly. It's a guided query-building tool — the user doesn't need to know the exact terminology CEKA uses internally.

Currently the counts on chips are randomised (placeholder). In production these should be live counts from a Supabase RPC or a pre-computed `search_tag_stats` table.

---

### 4. Rest State Feed (Two Levels)

**Level A — Trending (no profile):** Queries bills and blog posts created in the last 72 hours, sorted by recency. Pure time-based. Shows Kenya what's moving right now.

**Level B — Personalised (profile exists):** Uses the user's `areas_of_interest`, `interests`, and `county` from your profiles table. Fires 4 parallel queries with Supabase's `tags.cs.{}` (contains) operator to find content where the tags array contains any of the user's interests. County is appended as an additional OR condition. Results are scored with the full composite algorithm (no query tokens, so interest matching takes 100% of the match score weight). Falls back to trending if no interests are set.

---

### 5. The Hook (`useSearch`)

Debounced at 320ms — fast enough to feel responsive, slow enough to not hammer Supabase on every keystroke. AbortController on every new query — if you type fast, previous in-flight requests are cancelled. State machine handles 5 distinct modes: loading, rest-with-profile, rest-without-profile, active-with-results, active-without-results.

---

### 6. The UI (`SearchPage`)

- **Sticky header** at `z-50` with backdrop blur — search bar, chips, filter tabs all live here
- **Enrichment chips** animate in/out with Framer Motion height animation — zero layout shift
- **Filter tabs** appear only when results exist — Bills / Blog / Resources / Community with live counts
- **Score pills** on every card — green above 70%, amber 40–70%, grey below 40%
- **Skeleton loading** — 4 pulsing placeholder cards while queries execute
- **Empty state** — contextual messaging depending on whether it's a failed search or cold start

## What Was NOT Implemented But Should Be

### pgvector Semantic Search
The biggest missing piece. Right now search is `ilike` — keyword matching. A Kenyan user searching "bei ya unga" won't find a bill titled "Cost of Living Amendment Act 2026" even though they're the same thing. With pgvector you embed all content at write time using OpenAI or a lightweight open model via Supabase Edge Functions. At query time you embed the search query and do cosine similarity against the stored vectors. You'd get semantically correct results across language barriers, synonyms, and Sheng. Supabase has a guide for automatic embeddings with `pgmq + pg_net + pg_cron` — you already have all the infrastructure.

### Full-Text Search with `tsvector`
A middle ground between ilike and pgvector. PostgreSQL's native FTS using `to_tsvector` and `to_tsquery`. Much faster than ilike on large tables, handles stemming (so "taxation" matches "tax"), and supports ranking with `ts_rank`. You'd add a generated `search_vector` column to each table, index it with GIN, and query with `.textSearch()` in Supabase. This should replace the current ilike queries even before you add pgvector.

### Swahili / Multilingual Search
Your profiles table has `preferred_lang`. Right now the algorithm ignores it entirely. With pgvector this becomes trivial — multilingual embeddings handle cross-language retrieval naturally. Without it, you'd need a parallel keyword map in Swahili and potentially Sheng for the enrichment chip system.

### Search History & Learning
Your profiles table has `preferences jsonb`. You could store a user's search history there, or better yet in a dedicated `search_history` table. Then the algorithm could boost content from topics the user has repeatedly searched. Repeated searches for "devolution" should permanently increase the weight of devolution-tagged content in that user's feed, not just during the current session.

### Live Chip Counts from Supabase
Right now enrichment chip counts are `Math.random()`. They should be a Supabase RPC — a function that takes an array of tags and returns real counts from your content tables. A single call, runs in the database, cached per session.

### `pg_cron` Trending Cache
`fetchTrending()` currently hits the database live on every page load. With `pg_cron` you'd run a scheduled function every 15 minutes that writes the top trending items into a `trending_cache` table. The search page reads from that cache instead — one indexed read instead of a multi-table aggregation query on every visit.

### Search Analytics Table
A `search_events` table: `user_id, query, results_count, clicked_result_id, clicked_result_type, timestamp`. Every search and every click gets logged. This gives you the data to know what Kenyans are actually searching for on CEKA, which queries return zero results (content gaps), and which results get clicked vs ignored (relevance signal). This feeds directly back into improving the algorithm weights.

### Personalisation Feedback Loop
Currently the scoring weights (50/30/20) are hardcoded constants. In a more mature version, these weights should be per-user, updated based on their behaviour. If a user always clicks blog posts over bills, their match score weight for blog content should increase. This is a lightweight collaborative filtering layer — no ML needed, just a `user_content_weights` JSONB column on profiles updated by Edge Functions.

### PostGIS County Radius Search
Your profiles table has `county` as a text field. A user in Kiambu is probably interested in Nairobi content too — they're adjacent. With PostGIS you'd represent Kenya's 47 counties as geometries and weight nearby counties fractionally rather than the current binary match/no-match. County score becomes a gradient: exact match = 1.0, adjacent county = 0.6, same region = 0.3, elsewhere = 0.0.

### Real-Time Result Updates via Supabase Realtime
Supabase's Realtime lets you subscribe to Postgres changes. When a new bill is added or a blog post is published while the user is on the search page, it could surface at the top of the feed with a "New" indicator — no refresh needed. Particularly powerful for the 2027 election cycle when bills and reports will be landing fast.

### Offline Search Cache
Your CEKA Capacitor Android build should cache the last search results and personalised feed in AsyncStorage or SQLite. When the user opens the app offline, they see stale but relevant content rather than an error. Particularly important for low-connectivity areas outside Nairobi.

### Edge Function for Score Computation
Currently all scoring happens client-side in JavaScript. Moving `computeRelevanceScore` into a Supabase Edge Function means the scoring happens on the server, the client receives pre-ranked results, and you can use server-side data (like view counts, engagement metrics) that you'd never want to expose to the client directly.

### Contribution Points Integration
Your profiles table has `contribution_points`. Content created by high-contribution users could receive a small trust boost in the ranking — civic experts' blog posts and discussions surface slightly higher than new contributors'. A transparent credibility signal baked into the algorithm.

### Translation Role Awareness
Profiles have `translation_role` — contributor, reviewer, admin. When a user's preferred language is set and a translation exists for a piece of content, the search should surface the translated version. The algorithm currently returns content in whatever language it was created in.

## THE MOMENT A USER OPENS THE SEARCH PAGE

Before a single character is typed, the system is already working. The `useSearch` hook fires two async operations the instant the component mounts.

**Operation 1: `fetchTrending`**
Supabase receives two parallel queries — one against `bills`, one against `blog_posts`. Both are filtered with `.gte('created_at', since)` where `since` is `Date.now() - 72 hours`. Both are ordered by `created_at` descending. Both have a limit of 8. The results come back as raw Supabase rows. Each row is normalised into the unified `SearchResult` interface — same shape regardless of which table it came from. Then every result gets `recencyScore()` called against its `created_at`. That score becomes the `relevanceScore` for trending (no match or county component — pure time). The array is sorted descending and the top 8 land in `setTrending()`.

**Operation 2: `fetchPersonalised`** (only if `userProfile` is not null)
This queries your actual Supabase `profiles` table row for this user. It reads three fields: `areas_of_interest` (JSONB array), `interests` (JSONB array), and `county` (text). These are merged into one `allInterests` array. Then four parallel Supabase queries fire — bills, blog_posts, resources, community_posts — each using Supabase's `.or()` builder to construct a contains query:

```sql
tags.cs.{"Taxation"}, tags.cs.{"Healthcare"}, county.eq.Nairobi
```

This is PostgreSQL's `@>` operator under the hood — checking if the JSONB `tags` array contains a given value. Every matched row is normalised and run through `computeRelevanceScore()` with empty `queryTokens` (no query yet). The full 50/30/20 weighting applies but the match score component (50%) is driven entirely by `interestMatchScore` since there are no query tokens. Results sorted descending. Top 12 land in `setPersonalized()`.

The UI is now showing either the personalised feed (if profile exists and has interests) or the trending feed (if no profile or empty interests). The user hasn't typed a single character.

## THE MOMENT THE USER STARTS TYPING

The input field is a controlled React input. Every keystroke calls `setQuery()` which updates the `query` state. Two effects fire in parallel on every `query` change.

**Effect 1: Chip Extraction (immediate, no debounce)**
`extractEnrichmentChips(query)` runs synchronously on every character. It lowercases the query and checks it against the `CIVIC_KEYWORD_MAP`. This map has 10 civic domains hardcoded. The moment the query contains "finance", "bill", "election", "health", "education", "land", "tax", "devolution", "rights", or "water" — the corresponding chip array is returned. So typing "fi" does nothing. Typing "fin" does nothing. Typing "fina" does nothing. Typing "finan" — still nothing. Typing "financ" — the "finance" key matches. Five chips appear: `#Amendment`, `#TaxExemption`, `#KRA`, `#2026Budget`, `#PublicDebt`. These animate in via Framer Motion's height transition — they expand from zero height with opacity fade, no layout shift.

If the query has no civic keyword match but has words longer than 3 characters, it falls back to extracting those words as chips. So "John Mbadi" produces `#John` and `#Mbadi` as chips. These are passive suggestions — none are active by default.

**Effect 2: Search Execution (debounced 320ms)**
`useDebounce` from `use-debounce` holds the query in a separate `debouncedQuery` state that only updates 320ms after the user stops typing. This means if someone types "finance bill 2026" in one smooth motion, only one search fires — for the complete phrase — not 18 separate searches. The moment `debouncedQuery` changes, a new `AbortController` is created. The previous controller is aborted, cancelling any in-flight Supabase request that hasn't resolved yet. `setIsLoading(true)` fires, `setError(undefined)` clears any previous error, and `executeSearch()` begins.

## INSIDE `executeSearch` — THE FULL QUERY PIPELINE

The function receives: the Supabase client, the raw query string, an array of active chip labels (the ones the user has toggled), the user's profile object (or null), and a limit (default 20).

**Step 1: Query Assembly**
The raw query and all active chip labels are joined into one `fullQuery` string. Chips have their `#` prefix stripped. So if the user typed "finance bill" and has `#Amendment` and `#2026Budget` active, `fullQuery` becomes `"finance bill Amendment 2026Budget"`. This is then split on spaces to produce `tokens`: `["finance", "bill", "Amendment", "2026Budget"]`.

**Step 2: The Four Parallel Queries**
`Promise.allSettled` fires four Supabase queries simultaneously. This is the critical architectural decision — `allSettled` not `Promise.all`. If `community_posts` doesn't exist in your schema yet, or has an RLS policy that blocks this user, the other three queries complete normally. The search never white-screens.

**Bills query:**
```typescript
supabase
  .from('bills')
  .select('id, title, summary, tags, county, created_at, bill_number, status, ministry')
  .or(tokens.map(t => `title.ilike.%${t}%,summary.ilike.%${t}%`).join(','))
  .limit(20)
```
For 4 tokens this generates: `title.ilike.%finance%,summary.ilike.%finance%,title.ilike.%bill%,summary.ilike.%bill%,title.ilike.%Amendment%,summary.ilike.%Amendment%,title.ilike.%2026Budget%,summary.ilike.%2026Budget%`. PostgreSQL evaluates these as OR conditions. A row matches if any single one is true. This is deliberately broad — precision comes from the scoring layer, not the query layer.

**Blog posts query:** Same structure, targets `title` and `excerpt`, adds `.eq('status', 'published')` so drafts never appear.

**Resources query:** Targets `title` and `description`.

**Community posts query:** Targets `title` and `content`. The `content` field can be long — this is the only query where the ilike runs against potentially large text bodies.

**Step 3: Normalisation**
Each settled result is checked: `if (result.status === 'fulfilled' && result.value.data)`. Rejected promises are silently skipped — no crash, no error shown to user, the other results still render. Each raw row from each table is mapped to the unified `SearchResult` shape. The `type` field (`'bill' | 'blog' | 'resource' | 'discussion'`) is hardcoded per table. The `url` field is constructed from the type and ID — this is the navigation target when the card is tapped. The `metadata` field carries type-specific extras that don't fit the unified shape: bill_number and status for bills, author_name for blogs, category for resources, upvotes for discussions.

## INSIDE `computeRelevanceScore` — THE FULL SCORING MATHEMATICS

This function is called once per result, per search. If 80 results come back across 4 tables, it runs 80 times. It is intentionally pure — no side effects, no async, no Supabase calls.

**Match Score calculation (weight: 50% of final)**

First the query token hit ratio:
```typescript
const haystack = `${item.title} ${item.excerpt}`.toLowerCase();
const hits = queryTokens.filter(t => haystack.includes(t.toLowerCase())).length;
qMatch = Math.min(1.0, hits / queryTokens.length);
```
If the query has 4 tokens and the title+excerpt contain all 4: `qMatch = 1.0`. If it contains 2: `qMatch = 0.5`. This is a linear ratio, capped at 1.0.

Then the interest match score via `interestMatchScore()`:
```typescript
const normalise = (s: string) => s.toLowerCase().trim();
const userSet = new Set(userInterests.map(normalise));
```
Every user interest is lowercased and trimmed. Every item tag is lowercased. For each item tag, two checks happen: exact match against the user set (full point), and partial match — does the tag string contain any interest word, or vice versa (half point). So a user with interest "Tax" will get a 0.5 match bonus on an item tagged "TaxExemption" even without an exact match. The raw count is divided by the user interest set size (not the tag count) and capped at 1.0.

When a query is present, these two sub-scores blend:
```
mScore = qMatch × 0.6 + interestMatch × 0.4
```
The query hit is weighted higher (0.6) because the user is actively expressing intent. When no query (rest state), `mScore = interestMatch` alone — pure profile relevance.

**Recency Score calculation (weight: 30% of final)**
```typescript
function recencyScore(createdAt: string): number {
  const hoursOld = (Date.now() - new Date(createdAt).getTime()) / (1000 * 60 * 60);
  if (hoursOld <= 24)   return 1.0;
  if (hoursOld <= 72)   return 0.85;
  if (hoursOld <= 168)  return 0.65;
  if (hoursOld <= 720)  return 0.40;
  if (hoursOld <= 2160) return 0.20;
  return 0.05;
}
```
This is a stepped decay, not a smooth curve — intentional. A smooth exponential decay would almost always return near-zero for anything older than a week, making older but highly relevant content unfindable. The stepped approach means a 2-month-old landmark bill still scores 0.20 on recency — enough to rank above a fresh irrelevant post when the match score is high.

**County Score calculation (weight: 20% of final)**
```typescript
function countyScore(itemCounty?: string, userCounty?: string): number {
  if (!itemCounty || !userCounty) return 0.5;
  return itemCounty.toLowerCase() === userCounty.toLowerCase() ? 1.0 : 0.0;
}
```
Three possible states: 1.0 (exact county match), 0.5 (neutral — national content or profile has no county set), 0.0 (different county). The 0.5 neutral is the most important design decision here — national content (a Finance Bill with no county tag) doesn't get penalised for not being county-specific. It gets the same neutral county treatment as a Mombasa user searching on a Nairobi-county-tagged item.

**Final composite:**
```
relevanceScore = matchScore × 0.50 + recencyScore × 0.30 + countyScore × 0.20
```
All three sub-scores are stored on the result object individually. The UI shows the composite as a percentage pill on each card. This means a civic educator reviewing the results can literally see: "this bill is scoring 78% — high match, medium recency, no county tag."

## AFTER SCORING — SORT AND RETURN

The full results array (up to 80 items across 4 tables) is sorted by `relevanceScore` descending. The single best result regardless of type sits at position 0. A bill from 3 months ago with a perfect match score and county match will rank above a brand-new blog post with no match. This is the correct behaviour — relevance over recency.

The sorted array returns to `useSearch`, which calls `setResults()`. `setIsLoading(false)` fires. The UI transitions from skeleton to results.

## THE UI RENDER CYCLE — EVERY STATE

**State 1: Cold start, no profile**
`isRestState = true`. `personalized` is empty. `feed` resolves to `trending`. 8 cards rendered, each a recency-scored mix of recent bills and blog posts. Section heading shows "Trending in Kenya" with a `TrendingUp` icon.

**State 2: Cold start, profile exists with interests**
`isRestState = true`. `personalized` has results. `feed` resolves to `personalized`. Section heading shows "Suggested for you" with a `Bookmark` icon. The cards are the same component — `ResultCard` — but the content is profile-matched.

**State 3: Typing, chips not yet appeared**
Query is 1–2 characters. `debouncedQuery` hasn't updated. `chips` is empty (query too short for chip extraction). Loading state is false. Feed is still visible. Nothing changes visually yet.

**State 4: Civic keyword detected, chips appear**
Query crosses a keyword boundary. `chips` array populates. Framer Motion `AnimatePresence` detects the chips entering. The chip row animates in with `height: 0 → auto` and `opacity: 0 → 1` — no layout jump because `overflow: hidden` on the wrapper. Each chip renders with its label and count badge. All inactive (grey) by default.

**State 5: Debounce fires, search executing**
320ms after last keystroke. `isLoading = true`. The results area shows 4 skeleton cards with `animate-pulse`. The feed disappears — `isRestState` is now false, `hasResults` is still false.

**State 6: Results arrive**
`setResults()` fires. `isLoading = false`. The skeleton unmounts. Results mount with staggered animation — each card enters with `opacity: 0, y: 16` and transitions to `opacity: 1, y: 0` with a delay of `index × 0.04s`. So card 0 appears immediately, card 10 appears 400ms later. This creates a cascade waterfall effect, not a jarring simultaneous pop.

**State 7: Filter tab selection**
User taps "Bills" tab. `activeFilter` state updates to `'bill'`. `filteredResults` recomputes synchronously — just a `.filter()` on the already-scored array. No new Supabase query. The tab shows a live count badge. Cards that don't match the filter type unmount. The remaining ones re-render in their existing positions.

**State 8: Chip toggle**
User taps `#Amendment`. `toggleChip('#Amendment')` sets that chip's `active` to true. The chip re-renders in green with a shadow. The `chips` state change triggers the `debouncedQuery` effect (chips are a dependency). A new search fires 320ms later with `#Amendment` appended to the query. Results update. The chip is now acting as a persistent query modifier.

**State 9: Zero results**
`filteredResults.length === 0` and `!isRestState`. The `EmptyState` component mounts: icon, "No results for 'query'" text, suggestion to remove a chip. No crash, no blank page.

**State 10: Clear button**
The X button appears with `AnimatePresence` the moment `query` is truthy. Tapping it calls `clearQuery()` — sets query to empty string, clears results, clears chips. The filter tabs disappear (they animate out with `AnimatePresence`). The feed reappears. The component is back to State 1 or 2.

## WHAT IS NOT YET BUILT BUT IS THE NEXT LAYER

### PostgreSQL `tsvector` Full-Text Search — The Immediate Upgrade

Right now every search is `ilike`. On your `bills` table with 527 rows it's fast enough. At 5,000 rows it slows. At 50,000 community posts it breaks. The correct immediate upgrade is adding a generated column:

```sql
ALTER TABLE bills
ADD COLUMN search_vector tsvector
GENERATED ALWAYS AS (
  to_tsvector('english', coalesce(title, '') || ' ' || coalesce(summary, ''))
) STORED;

CREATE INDEX bills_search_vector_idx ON bills USING GIN(search_vector);
```

Then the query becomes:
```typescript
supabase
  .from('bills')
  .select('...')
  .textSearch('search_vector', tokens.join(' & '), { type: 'websearch' })
```

This uses Postgres's native GIN index — orders of magnitude faster than ilike, handles stemming, returns a `ts_rank` you can incorporate into the scoring. The `websearch` type handles natural language input including AND/OR operators that users might type.

### pgvector Semantic Search — The Intelligence Layer

This is the transformative upgrade. The reason it matters for CEKA specifically: a Kenyan user in Kisumu might search in Dholuo. A Nairobi youth might search in Sheng. A civic educator might search with formal legal terminology. All three might be looking for the same bill. `ilike` returns zero results for all of them. pgvector returns the correct bill for all of them.

The pipeline:
1. Every time a bill, blog post, resource, or community post is created or updated, a Supabase Edge Function fires via database trigger
2. The Edge Function calls OpenAI's `text-embedding-3-small` (cheapest, fast, multilingual) or Cloudflare Workers AI's `@cf/baai/bge-base-en-v1.5` (free on your existing CF account) with the content's title + body
3. The returned 1536-dimensional (OpenAI) or 768-dimensional (CF) float vector is stored in a new `embedding vector(1536)` column on each content table
4. A GIN index on the vector column enables fast cosine similarity search
5. At query time, the search query itself is embedded using the same model
6. A Supabase RPC runs `SELECT ... ORDER BY embedding <=> query_embedding LIMIT 20` — this is cosine similarity, returning the 20 semantically closest items

The scoring algorithm then incorporates the vector similarity score as a fourth dimension — potentially replacing or supplementing the current keyword match score entirely.

The automatic embedding pipeline using `pgmq` (message queue), `pg_net` (HTTP calls from Postgres), and `pg_cron` (scheduling) is documented in Supabase's own docs and directly applicable to your tables.

### Search Analytics — The Feedback Loop

A `search_events` table that captures everything:
```sql
CREATE TABLE search_events (
  id uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id uuid REFERENCES profiles(id),
  session_id text,
  query text NOT NULL,
  tokens text[],
  active_chips text[],
  results_count integer,
  result_types_returned text[],
  clicked_result_id text,
  clicked_result_type text,
  clicked_result_rank integer,
  clicked_relevance_score float,
  time_to_click_ms integer,
  zero_results boolean DEFAULT false,
  created_at timestamptz DEFAULT now()
);
```

Every search execution logs a row. Every card tap logs the click with the rank and score of what was clicked. This gives you:
- What Kenyans are actually searching for (query frequency)
- Which queries return zero results (content gap map)
- Which results get clicked vs ignored (precision signal — if rank 5 gets clicked more than rank 1, the scoring weights are wrong)
- Time-to-click (if the user clicks in 200ms they found what they wanted; if they scroll all the way to rank 15 and click, the top results aren't relevant)
- Session-level journey (what did they search before and after)

This data feeds directly back into adjusting the 50/30/20 weights. If county-matched content gets clicked 3x more than non-county content, the county weight should increase from 20% to 30%. This becomes an empirical calibration process, not a guess.

### Per-User Adaptive Weights — Personalisation Level 2

Currently every user gets the same 50/30/20 weights. In production, these should live in `profiles.preferences` as a JSONB object:

```json
{
  "search_weights": {
    "match": 0.50,
    "recency": 0.30,
    "county": 0.20
  },
  "type_affinity": {
    "bill": 1.2,
    "blog": 0.9,
    "resource": 1.0,
    "discussion": 0.8
  }
}
```

The `type_affinity` multipliers are updated by an Edge Function every time a user clicks a result. If they always click bills and never click discussions, `bill` affinity climbs toward 1.5 and `discussion` drops toward 0.6. This is lightweight collaborative filtering — no ML model needed, just a running average updated on every click event.

### `pg_cron` Trending Cache — Scaling the Rest State

Currently `fetchTrending` hits live tables on every page open. During the 2027 election cycle, with thousands of simultaneous users, this is a full table scan running in parallel hundreds of times per minute. The fix is a materialised trending cache:

```sql

  title text,
  excerpt text,
  tags text[],
  county text,
```

A `pg_cron` job runs every 15 minutes:
```sql

  DELETE FROM trending_cache;
  INSERT INTO trending_cache (...)
  SELECT ... FROM bills WHERE created_at > NOW() - INTERVAL '72 hours'
  UNION ALL
```

The search page reads from `trending_cache` — a single indexed scan of at most 20 rows. Microseconds instead of seconds.

### PostGIS Adjacent County Scoring — Geography Intelligence

Your current county scoring is binary. Nairobi matches Nairobi, doesn't match Kiambu — even though Kiambu residents shop, work, and engage civically in Nairobi daily. PostGIS fixes this.

Store Kenya's 47 county geometries in a `counties` table with PostGIS `GEOMETRY(MULTIPOLYGON, 4326)` columns. When computing county score:

```sql
SELECT ST_Distance(a.geom, b.geom) as distance
FROM counties a, counties b
WHERE a.name = 'Kiambu' AND b.name = 'Nairobi'
```

Distance 0 = same county → score 1.0. Adjacent (distance < 50km) → score 0.65. Same region (< 150km) → score 0.35. Elsewhere → score 0.0. This transforms county matching from a binary flag into a geographic gradient. The 20% weight stays the same — but now it's a continuous 0–1 value instead of 0 or 1.

You already identified the Ministry of Education schools shapefile (37,930 points) as high-impact for Nasaka IEBC. The counties geometry table is a natural companion to that — same PostGIS infrastructure, already on Pro plan.

function recencyScore(createdAt: string): number {
  const now = Date.now();
  const created = new Date(createdAt).getTime();
  const hoursOld = (now - created) / (1000 * 60 * 60);

  // Decay curve: full score within 24h, halves every 72h
  if (hoursOld <= 24) return 1.0;
  if (hoursOld <= 72) return 0.85;
  if (hoursOld <= 168) return 0.65; // 1 week
  if (hoursOld <= 720) return 0.40; // 1 month
  if (hoursOld <= 2160) return 0.20; // 3 months
  return 0.05;
}

function interestMatchScore(
  itemTags: string[],
  userInterests: string[]
): number {
  if (!userInterests.length || !itemTags.length) return 0;

  const normalise = (s: string) => s.toLowerCase().trim();
  const userSet = new Set(userInterests.map(normalise));
  const itemSet = itemTags.map(normalise);

  let matches = 0;
  for (const tag of itemSet) {
    if (userSet.has(tag)) matches++;
    // Partial match — tag contains interest word
    for (const interest of userSet) {
      if (tag.includes(interest) || interest.includes(tag)) {
        matches += 0.5;
        break;
      }
    }
  }

  return Math.min(1.0, matches / Math.max(userSet.size, 1));
}

function countyScore(itemCounty?: string, userCounty?: string): number {
  if (!itemCounty || !userCounty) return 0.5; // neutral if no county data
  return itemCounty.toLowerCase() === userCounty.toLowerCase() ? 1.0 : 0.0;
}

export function computeRelevanceScore(
  item: Omit<SearchResult, 'relevanceScore' | 'matchScore' | 'recencyScore' | 'countyScore'>,
  userProfile: UserProfile | null,
  queryTokens: string[]
): Pick<SearchResult, 'relevanceScore' | 'matchScore' | 'recencyScore' | 'countyScore'> {
  const allInterests = [
    ...(userProfile?.areas_of_interest ?? []),
    ...(userProfile?.interests ?? []),
  ];

  // Query match boost — direct text match in title/excerpt
  let qMatch = 0;
  if (queryTokens.length) {
    const haystack = `${item.title} ${item.excerpt}`.toLowerCase();
    const hits = queryTokens.filter(t => haystack.includes(t.toLowerCase())).length;
    qMatch = Math.min(1.0, hits / queryTokens.length);
  }

  const mScore = queryTokens.length
    ? qMatch * 0.6 + interestMatchScore(item.tags, allInterests) * 0.4
    : interestMatchScore(item.tags, allInterests);

  const rScore = recencyScore(item.created_at);
  const cScore = countyScore(item.county, userProfile?.county ?? undefined);

  // Weighted composite: Match 50% | Recency 30% | County 20%
  const relevance = mScore * 0.50 + rScore * 0.30 + cScore * 0.20;

  return {
    matchScore: parseFloat(mScore.toFixed(4)),
    recencyScore: parseFloat(rScore.toFixed(4)),
    countyScore: parseFloat(cScore.toFixed(4)),
    relevanceScore: parseFloat(relevance.toFixed(4)),
  };
}

  'water': ['#WaterAct', '#CountyWater', '#WRMA'],
};

export function extractEnrichmentChips(query: string): EnrichmentChip[] {
  const lower = query.toLowerCase();
  const chips: EnrichmentChip[] = [];

  for (const [keyword, tags] of Object.entries(CIVIC_KEYWORD_MAP)) {
    if (lower.includes(keyword)) {
      tags.forEach((tag, i) => {
        chips.push({ label: tag, count: Math.floor(Math.random() * 80 + 5), active: i === 0 });
      });
      break;
    }
  }

  // Fallback — extract significant words from query as chips
  if (!chips.length) {
    const words = query.split(' ').filter(w => w.length > 3);
    words.slice(0, 4).forEach(w => {
      chips.push({ label: `#${w}`, count: Math.floor(Math.random() * 30 + 2), active: false });
    });
  }

  return chips.slice(0, 5);
}

export async function executeSearch(
  supabase: ReturnType<typeof createClient>,
  query: string,
  activeChips: string[],
  userProfile: UserProfile | null,
  limit = 20
): Promise<SearchResult[]> {
  const fullQuery = [query, ...activeChips.map(c => c.replace('#', ''))].join(' ').trim();
  const tokens = fullQuery.split(' ').filter(Boolean);
  const results: SearchResult[] = [];

  // Run all 4 table searches in parallel
  const [billsRes, blogsRes, resourcesRes, discussionsRes] = await Promise.allSettled([

    // Bills
    supabase
      .from('bills')
      .select('id, title, summary, tags, county, created_at, bill_number, status, ministry')
      .or(tokens.map(t => `title.ilike.%${t}%,summary.ilike.%${t}%`).join(','))
      .limit(limit),

    // Blog posts
    supabase
      .from('blog_posts')
      .select('id, title, excerpt, tags, county, created_at, slug, author_name')
      .eq('status', 'published')
      .or(tokens.map(t => `title.ilike.%${t}%,excerpt.ilike.%${t}%`).join(','))
      .limit(limit),

    // Resources
    supabase
      .from('resources')
      .select('id, title, description, tags, county, created_at, file_url, category')
      .or(tokens.map(t => `title.ilike.%${t}%,description.ilike.%${t}%`).join(','))
      .limit(limit),

    // Community discussions
    supabase
      .from('community_posts')
      .select('id, title, content, tags, county, created_at, author_id, upvotes')
      .or(tokens.map(t => `title.ilike.%${t}%,content.ilike.%${t}%`).join(','))
      .limit(limit),
  ]);

  // Normalise bills
  if (billsRes.status === 'fulfilled' && billsRes.value.data) {
    billsRes.value.data.forEach((b: any) => {
      const base = {
        id: b.id,
        type: 'bill' as const,
        title: b.title,
        excerpt: b.summary ?? '',
        tags: b.tags ?? [],
        county: b.county,
        created_at: b.created_at,
        url: `/bills/${b.id}`,
        metadata: { bill_number: b.bill_number, status: b.status, ministry: b.ministry },
      };
      results.push({ ...base, ...computeRelevanceScore(base, userProfile, tokens) });
    });
  }

  // Normalise blog posts
  if (blogsRes.status === 'fulfilled' && blogsRes.value.data) {
    blogsRes.value.data.forEach((p: any) => {
      const base = {
        id: p.id,
        type: 'blog' as const,
        title: p.title,
        excerpt: p.excerpt ?? '',
        tags: p.tags ?? [],
        county: p.county,
        created_at: p.created_at,
        url: `/blog/${p.slug}`,
        metadata: { author: p.author_name },
      };
      results.push({ ...base, ...computeRelevanceScore(base, userProfile, tokens) });
    });
  }

  // Normalise resources
  if (resourcesRes.status === 'fulfilled' && resourcesRes.value.data) {
    resourcesRes.value.data.forEach((r: any) => {
      const base = {
        id: r.id,
        type: 'resource' as const,
        title: r.title,
        excerpt: r.description ?? '',
        tags: r.tags ?? [],
        county: r.county,
        created_at: r.created_at,
        url: r.file_url ?? `/resources/${r.id}`,
        metadata: { category: r.category },
      };
      results.push({ ...base, ...computeRelevanceScore(base, userProfile, tokens) });
    });
  }

  // Normalise community discussions
  if (discussionsRes.status === 'fulfilled' && discussionsRes.value.data) {
    discussionsRes.value.data.forEach((d: any) => {
      const base = {
        id: d.id,
        type: 'discussion' as const,
        title: d.title,
        excerpt: (d.content ?? '').slice(0, 200),
        tags: d.tags ?? [],
        county: d.county,
        created_at: d.created_at,
        url: `/community/${d.id}`,
        metadata: { upvotes: d.upvotes },
      };
      results.push({ ...base, ...computeRelevanceScore(base, userProfile, tokens) });
    });
  }

  // Sort by composite relevance score descending
  return results.sort((a, b) => b.relevanceScore - a.relevanceScore);
}

export async function fetchTrending(
  supabase: ReturnType<typeof createClient>,
  limit = 8
): Promise<SearchResult[]> {
  const since = new Date(Date.now() - 72 * 60 * 60 * 1000).toISOString();

  const [billsRes, blogsRes] = await Promise.allSettled([
    supabase
      .from('bills')
      .select('id, title, summary, tags, county, created_at, status')
      .gte('created_at', since)
      .order('created_at', { ascending: false })
      .limit(limit),

    supabase
      .from('blog_posts')
      .select('id, title, excerpt, tags, county, created_at, slug')
      .eq('status', 'published')
      .gte('created_at', since)
      .order('created_at', { ascending: false })
      .limit(limit),
  ]);

  const trending: SearchResult[] = [];

  if (billsRes.status === 'fulfilled' && billsRes.value.data) {
    billsRes.value.data.forEach((b: any) => {
      trending.push({
        id: b.id, type: 'bill', title: b.title, excerpt: b.summary ?? '',
        tags: b.tags ?? [], county: b.county, created_at: b.created_at,
        url: `/bills/${b.id}`, relevanceScore: recencyScore(b.created_at),
        matchScore: 0, recencyScore: recencyScore(b.created_at), countyScore: 0,
        metadata: { status: b.status },
      });
    });
  }

  if (blogsRes.status === 'fulfilled' && blogsRes.value.data) {
    blogsRes.value.data.forEach((p: any) => {
      trending.push({
        id: p.id, type: 'blog', title: p.title, excerpt: p.excerpt ?? '',
        tags: p.tags ?? [], county: p.county, created_at: p.created_at,
        url: `/blog/${p.slug}`, relevanceScore: recencyScore(p.created_at),
        matchScore: 0, recencyScore: recencyScore(p.created_at), countyScore: 0,
      });
    });
  }

  return trending.sort((a, b) => b.relevanceScore - a.relevanceScore).slice(0, limit);
}

function timeAgo(iso: string): string {
  const secs = Math.floor((Date.now() - new Date(iso).getTime()) / 1000);
  if (secs < 60) return 'just now';
  if (secs < 3600) return `${Math.floor(secs / 60)}m ago`;
  if (secs < 86400) return `${Math.floor(secs / 3600)}h ago`;
  if (secs < 604800) return `${Math.floor(secs / 86400)}d ago`;
  return new Date(iso).toLocaleDateString('en-KE', { day: 'numeric', month: 'short' });
}

## I. ARCHITECTURAL LOGIC & HARDENING PRINCIPLES

### 1. Punctuation-Agnostic Engine (`searchService.ts`)
**The Problem**: Users searching for "Finance Bill, 2026" (with punctuation) were failing exact-match checks because the engine treated the comma as part of the token.
**The Hardening**: We implemented a "Deep Sanitizer" pipeline. Every query is now stripped of non-alphanumeric characters *before* tokenization. 
- **Relevance Score Absolute**: Exact matches now hit a mandatory 200-point bonus, pinning them to the top of the "Top Record Match" vault.
- **Structural Dominance Penalty**: To prevent metadata-heavy records from floating to the top, we implemented a **-200 point penalty** if a query exists but no query tokens appear in the record's primary title.

### 2. Imperative Navbar Kill-Switch (`SearchSuggestion.tsx`)
**The Problem**: React's state-based dropdowns often persist during rapid navigation, creating a "Focus Loop" where the suggestion box stays open over the new page.
**The Hardening**: We bypassed standard declarative state for a "Manual Kill-Switch." 
- **Imperative Blur**: Using a `useRef` on the input, we trigger `inputRef.current?.blur()` on every `location.key` change.
- **Session Suppression**: We implement `ceka_search_suppress` in `sessionStorage` to ensure that when a user is redirected to the search page, the navbar "sleeps" and does not pop the dropdown again until a fresh manual interaction.

### 3. Linguistic JSON Sanitizer (`SearchResults.tsx`)
**The Problem**: Database excerpts were leaking raw JSON/Python dictionary strings like `{'plain_english': '...'}` into the user interface.
**The Hardening**: A robust `sanitizeExcerpt` utility was built into the results renderer. It attempts to parse JSON, falls back to Python-regex extraction, and finally strips all brackets and key-names to ensure a "Simple English" output.

```typescript
                tags: ['Glossary', 'Education'], created_at: item.created_at, date: item.created_at,
                url: `/education/glossary`, category: 'Knowledge'
              };
              break;
            case 'contact':
              base = {
                id: item.id, type: 'contact', title: item.name, description: item.description || '', excerpt: item.phone,
                tags: ['Hotline', 'Emergency'], created_at: item.created_at, date: item.created_at,
                url: `/hotlines`, category: item.organization, metadata: { phone: item.phone }
              };
              break;
            case 'media':
              base = {
                id: item.id, type: 'media', title: item.title, description: item.description || '', excerpt: (item.description || '').slice(0, 150),
                tags: item.tags || [], created_at: item.created_at, date: item.created_at, slug: item.slug,
                url: `/media/${item.slug}`, category: item.type
              };
              break;
          }
          if (base) {
            results.push({ ...base, ...this.computeRelevanceScore(item, userProfile, tokens, typeIntent) });
          }
        });
      }
    });

    return {
      items: results.sort((a, b) => b.relevanceScore - a.relevanceScore),
      total: results.length,
      facets: {
        'bills': 'Legislation',
        'laws': 'Constitution',
        'blog': 'Intelligence',
        'resources': 'Services'
      }
    };
  }
}
```

```typescript
import { useState, useEffect, useCallback, useRef } from 'react';
import { useAuth } from '@/providers/AuthProvider';

import { searchService, SearchResult, UserProfile, SearchFilters } from '@/lib/searchService';

export const useSearch = () => {
  const { user } = useAuth();
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebounce(query, 300);
  const [results, setResults] = useState<SearchResult[]>([]);
  const [chips, setChips] = useState<{ id: string, label: string, count: number, active: boolean }[]>([]);
  const [loading, setLoading] = useState(false);
  const [profile, setProfile] = useState<UserProfile | null>(null);
  const [page, setPage] = useState(0);
  const [hasMore, setHasMore] = useState(true);
  const [filters, setFilters] = useState<SearchFilters>({});

  useEffect(() => {
    if (!user) return;
    supabase.from('profiles').select('*').eq('id', user.id).single().then(({ data }) => {
      if (data) setProfile({ id: data.id, areas_of_interest: data.areas_of_interest || [], interests: data.interests || [], county: data.county });
    });
  }, [user]);

  const performSearch = useCallback(async (isNewSearch: boolean) => {
    setLoading(true);
    const currentPage = isNewSearch ? 0 : page;
    try {
      const response = await searchService.searchAll(debouncedQuery, profile, [], currentPage, 10, filters);
      if (isNewSearch) {
        setResults(response.items);
        setPage(0);
        if (debouncedQuery.length > 2) setChips(await searchService.getEnrichmentChips(debouncedQuery, response.items));
        else setChips([]);
      } else {
        setResults(prev => [...prev, ...response.items]);
      }
      setHasMore(response.items.length === 10);
    } catch (error) { console.error('Search yield failed:', error); } finally { setLoading(false); }
  }, [debouncedQuery, profile, page, filters]);

  useEffect(() => { performSearch(true); }, [debouncedQuery, filters]);
  useEffect(() => { if (page > 0) performSearch(false); }, [page]);

  return { query, setQuery, results, chips, loading, loadMore: () => hasMore && setPage(p => p + 1), hasMore, filters, setFilters };
};
```
